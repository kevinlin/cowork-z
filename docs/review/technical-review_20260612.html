Executive Summary

This is a full-repository technical review of cowork-z, a Tauri 2.x desktop application that sandboxes autonomous AI agents via an OpenCode sidecar. It is a follow-up to the June 11, 2026 review, after which 19 of 35 findings were remediated and merged to main (see remediation tracker). This pass re-verified all deferred/unassessed items against the current code and hunted for new issues across the four layers: Rust backend (src-tauri/src/), Node.js sidecar (src-tauri/sidecar-opencode/), React frontend (src/), and build/CI/configuration.

Repository statistics

  • Total source files: 261 (TypeScript/TSX, Rust, CSS, HTML — excluding the legacy apps/desktop/ reference app, built binaries, generated .d.ts, and docs)
  • Total lines of code: 45,440
  • Layers: 46 Rust files (src-tauri/src/), Node sidecar (src-tauri/sidecar-opencode/src/), React 19 frontend (src/)

Findings by severity

  • CRITICAL 1 finding — the OpenCode server password is still shipped to model providers inside every system prompt (deferred from the prior review, unchanged).
  • HIGH 11 findings — several re-open the filesystem sandbox that the June remediation built (read_directory unscoped, unvalidated permission grants, skill-delete path traversal), plus a regression: the CI lint fix (#16 in the prior review) is documented as fixed but the workflow on main still backgrounds the lint with &.
  • MEDIUM 24 findings — correctness, robustness, and hardening gaps across all layers.
  • LOW 7 findings — maintainability and minor UX/consistency issues.

Carry-over status from the June 11 review: the deferred items #11 (password in system prompt), #12 (port TOCTOU), #25 (streaming markdown re-parse), #26 (Rust test coverage), #27 (get_key_prefix panic), #28 (unserialized stdin), #29 (IPC double casts), #30 (O(n²) chat scans), #31 (listener unsubscribe race), #33 (god-files), #34 (dead IPC code), and #35 (no dependency audit / .gitignore) all still exist and are re-reported below with current line numbers. The DB mutex poisoning fix (#9) is partial — ~20 .unwrap() sites remain in automation and startup paths.

1. OpenCode server password embedded in every LLM system prompt

CRITICAL

Summary: The sidecar injects the live HTTP basic-auth password for the local OpenCode server into the system prompt sent to the model provider on every turn. (Carry-over: deferred #11 from the June 11 review — unchanged.)

Details: buildSystemPrompt() interpolates serverPassword into agent-facing instructions, and session-manager.ts attaches that prompt to each sendMessage call. The bundled skill deployed on every app launch (resources/skills/opencode-server-api/SKILL.md) explicitly teaches the agent to extract the password from the prompt. Any provider-side logging, prompt retention, tool-output echo, or prompt-injection attack exposes a credential that grants full control of a localhost server able to run shell commands as the user.

Occurrences:

  • src-tauri/sidecar-opencode/src/config-builder.ts — lines 97–102
  • src-tauri/sidecar-opencode/src/session-manager.ts — lines 365, 421
  • src-tauri/resources/skills/opencode-server-api/SKILL.md — lines 5–13 (instructs the agent to read the password)
// config-builder.ts (97–102) Authenticate with: -u opencode:${serverPassword} Before calling any API endpoint, ALWAYS fetch the OpenAPI spec first: curl -s -u opencode:${serverPassword} http://localhost:${serverPort}/doc // session-manager.ts (365) system: buildSystemPrompt(this.serverPort, this.serverPassword, workingDirectory ?? '.', customPrompt),
Remediation: Remove the password from model context. Either proxy authenticated server calls through the sidecar (agent gets port-only instructions), or mint short-lived, scope-limited tokens per session instead of embedding the master server password. Agent self-access is a feature, but it must not ride on the root credential.

2. Unscoped read_directory allows arbitrary filesystem enumeration

HIGH

Summary: The June remediation guarded read_file_content, read_binary_file, and trash_file with path_guard, but read_directory accepts any absolute path with no workspace or permission check.

Details: A compromised webview (or any renderer bug) can enumerate /, $HOME, ~/.ssh, browser profiles, etc. Directory listings reveal filenames and structure that aid further attacks, undermining the sandbox model the rest of the file commands now enforce.

Occurrences:

  • src-tauri/src/commands/workspaces.rs — lines 176–185
#[tauri::command] pub async fn read_directory(path: String) -> Result<Vec<DirectoryEntry>, String> { let dir_path = Path::new(&path); if !dir_path.is_dir() { return Err(format!("'{}' is not a directory", path)); } let mut entries = Vec::new(); let read_dir = std::fs::read_dir(dir_path).map_err(|e| format!("Failed to read directory: {}", e))?;
Remediation: Apply the same path_guard::validate_path_in_roots pattern used in commands/files.rs — validate the canonicalized path against registered workspaces, granted permission folders, and app-managed roots before listing.

3. Workspace permission grants persisted without path validation widen the sandbox

HIGH

Summary: save_workspace_permission and respond_to_permission persist arbitrary folder_path strings and immediately call sync_asset_scope, adding them to the path_guard allowed roots and the asset: protocol scope.

Details: A malicious renderer call — or an agent-supplied permission pattern that a user clicks "Allow" on — can grant read/trash access to /, $HOME/.ssh, or any other directory. Because granted folders feed directly into the runtime asset scope (the mechanism introduced by remediation #2), this is the single easiest way to re-open the entire filesystem sandbox.

Occurrences:

  • src-tauri/src/commands/workspace_permissions.rs — lines 16–27
  • src-tauri/src/commands/tasks.rs — lines 548–558 (respond_to_permission persistence path)
let conn = state.conn.lock().map_err(|e| e.to_string())?; let source = source.as_deref().unwrap_or("user"); db::workspace_permissions::save_workspace_permission( &conn, &workspace_id, &folder_path, &access_level, source, )?; // Newly granted folders become loadable via the asset: protocol crate::path_guard::sync_asset_scope(&app, &conn);
Remediation: Canonicalize and validate every permission path before persisting or syncing the asset scope — at minimum apply workspace_validator rules (block system paths and the home root) and consider requiring grants to live under the workspace tree or an explicit, Rust-side user confirmation dialog.

4. Path traversal in skills_delete_installed via unsanitized skill_id

HIGH

Summary: skill_id is joined directly into the install path with no sanitization or canonicalization, then recursively deleted.

Details: A value like ../../.ssh or ../../../Documents resolves outside ~/.config/opencode/skills and is passed to remove_path, which deletes files or whole directory trees. The command is invokable from the webview (Skills Manager window), so a renderer compromise becomes arbitrary deletion under the user account.

Occurrences:

  • src-tauri/src/commands/skill_repos.rs — lines 515–532
let target = target_folder.as_deref().unwrap_or("opencode"); let install_dir = resolve_target_folder(target)?; let skill_dir = install_dir.join(&skill_id); if !is_symlink(&skill_dir) && !skill_dir.exists() { return Err(format!("Skill directory not found: {}", skill_dir.display())); } remove_path(&skill_dir)?;
Remediation: Reject any skill_id containing /, \, or ..; canonicalize the resolved path and verify it is still a direct child of install_dir before deletion. Audit target_folder handling in resolve_target_folder the same way.

5. All provider API keys sent in bulk over sidecar IPC on every task start

HIGH

Summary: Every start_task, resume_session, and automation dispatch loads all provider secrets from the OS keychain and serializes them as JSON onto the sidecar's stdin.

Details: The full credential set (Anthropic, OpenAI, Google, Bedrock, Azure, OpenRouter, LiteLLM, Copilot…) crosses the process boundary on each task, regardless of which provider the task actually uses. Any compromise of the sidecar process, its environment, crash dumps, or logs (see finding 6) exposes every stored credential at once, defeating the point of keychain storage.

Occurrences:

  • src-tauri/src/commands/tasks.rs — lines 134–166 (bulk load + send)
  • src-tauri/src/sidecar.rs — lines 508–513, 654–700 (serialization to stdin)
manager.send_command(sidecar::SidecarCommand::StartTask { task_id: task_id.clone(), payload: sidecar::StartTaskPayload { task_id: task_id.clone(), prompt: config.prompt.clone(), api_keys: Some(api_keys), // ← all providers' keys, every task ...
Remediation: Send only the active provider's credential per task, or remove keys from IPC entirely — have the sidecar request the specific secret it needs through a narrow, audited Rust bridge at server-spawn time.

6. API keys escape redaction into plaintext logs

HIGH

Summary: The redaction layer added in the June remediation (#4/#10) has a gap: full IPC commands are still logged, and the redactor's key-pattern misses provider field names — while Rust separately appends all sidecar stdout to a plaintext log file.

Details: logger.debug('Received command', msg) logs the entire start_task/resume_session payload. redactSecrets() only masks values whose key matches password|secret|token|apiKey|… — nested provider fields like anthropic, openai, or accessKeyId inside the apiKeys object do not match, so real keys reach disk logs and the frontend debug panel. Compounding this, the Rust side writes all sidecar stdout verbatim to ~/.local/share/opencode/log/*.log with no redaction and default file permissions. Combined with finding 5, every stored credential has a durable plaintext exposure path.

Occurrences:

  • src-tauri/sidecar-opencode/src/index.ts — line 645 (logger.debug('Received command', msg))
  • src-tauri/sidecar-opencode/src/redact.ts — lines 8, 40–42 (key pattern misses provider names)
  • src-tauri/src/sidecar.rs — lines 382–384, 415–425 (verbatim stdout capture to log file)
// index.ts logger.debug('Received command', msg); // full payload incl. apiKeys // redact.ts — only matches secret-looking key names if (SECRET_KEY_PATTERN.test(key) && (typeof val === 'string' || typeof val === 'number')) { result[key] = REDACTED; // 'anthropic', 'openai' don't match }
Remediation: Log only { type, taskId } for incoming commands, or redact the entire apiKeys container by name (as already done for environment/headers/env). Add a regression test for { apiKeys: { anthropic: 'sk-…' } }. On the Rust side, restrict log file permissions to 0600 and avoid persisting full stdout payloads by default.

Details: pnpm ultracite:check & pnpm test --run backgrounds the lint; the step's exit code comes from Vitest alone. Lint and format violations merge to main unnoticed, and the team believes this gate is active because the tracker marks it fixed — a worse state than before the remediation.

8. Unserialized concurrent stdin command handling in the sidecar

HIGH

Summary: Each JSON line on stdin spawns an async handleMessage() with no queue or mutex, so overlapping commands race on shared state. (Carry-over: #28 from the June 11 review — unchanged.)

Details: Overlapping start_task + shutdown, two simultaneous task starts, or OAuth + task start can race on processManager, sessionManager, initializePromise, and SSE reconnection — producing duplicate server spawns, lost shutdown ordering, or interleaved IPC events. The readline line handler does not await the previous handler before dispatching the next.

Occurrences:

  • src-tauri/sidecar-opencode/src/index.ts — lines 644–738 (handler), 784–787 (dispatch)
rl.on('line', async (line: string) => { const msg = JSON.parse(line) as SidecarCommand; await handleMessage(msg); // each line runs concurrently — rl doesn't await });
Remediation: Serialize handling with a promise chain (queue = queue.then(() => handleMessage(msg))) or an explicit FIFO command queue; reject or buffer commands once shutdown begins.

9. sendMessage failures swallowed — tasks hang with no error surfaced

HIGH

Summary: Initial and follow-up messages to the OpenCode server are fire-and-forget; a rejected sendMessage only produces a logger.warn, never a task_error IPC event.

Details: If session creation succeeds but the message call fails (network blip, auth error, model error), the UI shows an active task that never progresses and never errors. The user has no signal to retry, and the orphaned session is left in place.

Occurrences:

  • src-tauri/sidecar-opencode/src/session-manager.ts — lines 361–375 (initial), 417–431 (follow-up)
this.client.sendMessage(session.id, { /* ... */ }) .catch((err) => { logger.warn('sendMessage request failed (session may still be active via SSE)', { taskId, sessionId: session.id, error: msg, }); // ← no task_error emitted; UI keeps spinning });
Remediation: On rejection, emit a task_error IPC event (unless SSE has already confirmed the turn started) and abort the orphaned session so the UI can present a retry.

11. Arena mode double-persists and never dedupes task events

HIGH

Summary: While Arena is open, every task event is persisted to SQLite twice — once by the global taskStore listener and once by arenaStore.handleTaskUpdate — and the arena handler appends messages without the ID-dedup logic the task store uses.

Details: The June remediation (#20) consolidated persistence into a single module-level onTaskUpdate subscription in taskStore.ts, which unconditionally saves messages/completions for all task IDs. Arena.tsx registers parallel listeners whose handler also calls saveTaskMessage/completeTask for arena tasks — duplicate rows in SQLite and duplicate lifecycle side effects. Separately, arenaStore appends [...task.messages, event.message] with no dedup, so a re-delivered event produces duplicate UI rows.

Occurrences:

  • src/stores/taskStore.ts — lines 822–848 (global persistence), 1219–1225 (subscription)
  • src/stores/arenaStore.ts — lines 412–438 (second persistence path), 445–451 (append without dedup)
  • src/pages/Arena.tsx — lines 59–64 (parallel listener registration)
// taskStore.ts (global, all task IDs) api.saveTaskMessage(event.taskId, event.message).catch(...) // arenaStore.ts (arena tasks, same event) api.saveTaskMessage(event.taskId, event.message).catch(...) ... col.task = { ...task, messages: [...task.messages, event.message] }; // no dedup
Remediation: Make persistence single-owner: skip arena task IDs in the global handler (or vice versa), and mirror taskStore's index-by-message-ID merge in the arena handler.

12. Streaming pipeline re-parses full markdown and re-renders the whole page per delta

HIGH

Summary: Every streaming delta triggers a full remark/GFM parse of the growing message and a re-render of the entire Execution page. (Markdown re-parse is carry-over #25 from the June 11 review — unchanged; the page-wide re-render is new.)

Details: Each partial update flows through displayContent → normalizedContent → enrichedContent into ReactMarkdown inside StreamingText's render prop, re-parsing the whole string per delta. Worse, Execution.tsx destructures the entire useTaskStore() without selectors — including partialMessages, a Map replaced on every delta — so the full page (header, every MessageBubble, modals, input) re-renders at streaming frequency. Long answers degrade typing latency and burn CPU.

Occurrences:

  • src/components/chat/MessageBubble.tsx — lines 57–63, 158–165
  • src/components/ui/streaming-text.tsx — lines 104–107
  • src/pages/Execution.tsx — lines 47–62 (whole-store subscription)
// Execution.tsx — subscribes to the entire store, incl. partialMessages const { currentTask, loadTaskById, isLoading, error, ..., partialMessages } = useTaskStore(); // MessageBubble.tsx — full ReactMarkdown parse per streaming delta <StreamingText isComplete={false} isRealStreaming={true} speed={120} text={enrichedContent}> {(displayedText) => ( <ReactMarkdown components={markdownComponents} remarkPlugins={[remarkGfm]} ...> {displayedText} </ReactMarkdown>
Remediation: Use granular Zustand selectors (useTaskStore(s => s.currentTask), useShallow) and isolate streaming state in a child component. During live streaming, render plain text (or throttle markdown parsing to 100–200 ms) and switch to full ReactMarkdown on message completion.

15. Workspace validator allows any non-home path without canonicalization

MEDIUM

Summary: After blocking known system prefixes and the home root, validate_workspace_path falls through to Ok(()) for any other absolute path, without resolving symlinks.

Details: Users (or a compromised renderer) can register /tmp, /opt, another user's directory, or a symlink whose target escapes the intended tree. Because workspace roots feed path_guard and the asset scope, this widens the file-access surface established by the June remediation.

Occurrences:

  • src-tauri/src/workspace_validator.rs — lines 91–103
if let Some(home) = dirs::home_dir() { if folder_path == home_str.as_ref() { return Err("Your home directory cannot be used as a workspace. ...".to_string()); } if path.starts_with(&home) { return Ok(()); } } Ok(()) // ← any non-home absolute path is accepted
Remediation: Canonicalize before validating, reject symlinked escapes, and either restrict workspaces to $HOME subtrees (plus removable volumes) or require explicit confirmation for out-of-home paths.

16. Database migrations are not transactional

MEDIUM

Summary: Each schema migration runs multi-statement DDL without a wrapping transaction; a crash mid-migration leaves the database in an inconsistent state.

Details: Migrations like v6 (which drops and recreates folder_permissions with a data copy) execute as standalone statements. If the process dies between the copy and the drop, the schema version is wrong relative to the actual tables, and the app cannot self-recover on next launch.

Occurrences:

  • src-tauri/src/db/migrations.rs — lines 398–451 (orchestration), 311–331 (v6 batch)
pub fn run_migrations(conn: &Connection) -> Result<(), String> { let stored_version = get_stored_version(conn); if stored_version < 1 { migrate_v1(conn)?; } // ... each migrate_vN runs DDL without BEGIN/COMMIT
Remediation: Wrap each migration in BEGIN IMMEDIATE … COMMIT and only bump schema_meta.version inside the same transaction.

17. DB layer panics: .expect() on queries and residual .lock().unwrap()

MEDIUM

Summary: Core DB read helpers panic on prepare/query failure, and ~20 mutex-lock sites still use .unwrap(). (Mutex poisoning is carry-over #9 from the June 11 review — partially fixed: command handlers now propagate errors, but automation and startup paths do not.)

Details: A corrupted DB, schema drift, or disk error in db/tasks.rs (10 .expect() calls; similar in db/workspaces.rs, db/providers.rs, db/workspace_permissions.rs, db/arenas.rs) crashes the process instead of surfacing an error. Remaining .lock().unwrap() sites in commands/automations.rs (73–254), automation_scheduler.rs (14 sites), lib.rs (118, 166, 188), commands/updates.rs (40, 56), and the log-file mutexes in sidecar.rs (285, 397) re-introduce cascading panics once the mutex is poisoned.

Occurrences:

  • src-tauri/src/db/tasks.rs — lines 114–138 and throughout
  • src-tauri/src/automation_scheduler.rs — lines 44–422 (14 .unwrap() sites)
  • src-tauri/src/commands/automations.rs — lines 73–254
  • src-tauri/src/lib.rs — lines 118, 166, 188
.expect("Failed to prepare messages query"); // ... .expect("Failed to query messages"); // automation_scheduler.rs let conn = db_state.conn.lock().unwrap();
Remediation: Propagate Result through the DB layer (? instead of .expect()), and finish the mutex remediation with a shared helper that recovers from poisoning (unwrap_or_else(|p| p.into_inner())) or maps to an error.

MEDIUM

Details: Commands sent during sidecar initialization (Node startup, PATH resolution, server boot) can be lost or race with server startup, producing intermittent first-task failures that are hard to reproduce.

Occurrences:

Remediation: Gate is_running()/send_command on receipt of the ready event with a timeout, queueing or rejecting commands until then.

Details: Agents routinely write into nested folders; the sidebar file tree and artifacts panel will appear stale for anything below the top level, which users perceive as the agent "not doing anything".

20. TOCTOU race in ephemeral port selection

MEDIUM

Summary: The sidecar binds port 0 to discover a free port, closes the probe socket, then spawns opencode serve on that port later. (Carry-over: deferred #12 from the June 11 review — unchanged.)

Details: Between close and spawn, another process can claim the port, causing startup failure — or, worse on localhost, the sidecar could authenticate against a different listener squatting the port.

Occurrences:

  • src-tauri/sidecar-opencode/src/process-manager.ts — lines 276–307 (getAvailablePort), 469–505 (spawn)
server.close(() => { resolve(port); }); // ... later ... this.port = await getAvailablePort(); const args = ['serve', '--port', String(this.port), '--hostname', this.hostname]; this.process = spawn(this.cliPath, args, { /* ... */ });
Remediation: Pass --port 0 to opencode serve and parse the bound port from its startup output, or add bounded retry on bind failure with server-identity verification (auth challenge) before first use.

21. Stale sessions cleaned up locally but never aborted on the server

MEDIUM
